What this app is: Harvey-caliber legal AI for self-represented (pro se) litigants. It organizes a case, drafts filings, tracks deadlines, and — its defining feature — verifies every legal citation against a real primary source (CourtListener API) before it ever reaches a document. Models draft; deterministic code verifies. That principle governs everything below.

PHASE 3 — Auth

Supabase authentication: email/password AND Sign in with Apple. Gate the entire app behind login. First login lands on the Cases list with an empty state inviting "Start your first case."


PHASE 4 — Case object + guided chat

A user creates a case (title, case type, court, parties). Opening a case shows the guided chat built from the Phase 1 components. Critical behavior: the Navigator speaks first. Each case type has an intake script — an opening message plus an ordered set of questions — so the user never faces a blank box. Under every Navigator turn, render tappable next-step rows (the available paths forward). Tapping one sends it as the user's reply. Persist all messages to messages, scoped to the case.


PHASE 5 — RAG memory per case

Document upload (PDF/image) to a case. On upload: extract text, chunk it, generate embeddings, store in document_chunks. On every chat turn: retrieve top-k relevant chunks + recent messages + the case's structured fields, and pass that bundle as context to the model call. Each case has persistent memory of its own documents only (RLS-scoped).

PHASE 7 — Verification gate (Edge Function: verify) — THE defining feature

Ask me for: <<COURTLISTENER_API_TOKEN>>.

Before ANY drafted text containing a legal citation is shown to the user or inserted into a document:


Extract every citation from the draft.
Check each against the CourtListener API.
Confirmed real (and quote confirmed where applicable) → mark verified (green), store in verified_authorities with the URL.
Cannot confirm → flag red and DO NOT insert it. Never silently include an unverified citation.


This runs on every draft, on every plan including Free. It is deterministic code, not a model judgment.


PHASE 8 — Deadline engine (deterministic code, never the LLM)

When the user enters a trigger date (default anchor: service date, not filing date), compute the deadline in code using federal Rule 6 counting: exclude the first day, include the last day, roll weekends/federal holidays to the next business day. Federal defaults first (e.g., 21-day answer window). Display the computed deadline immediately with the rule used and the note: "Confirm against your court's rules." Save to deadlines.

If an answer deadline passes with no response logged: surface the two-step default process — Rule 55(a) clerk's entry of default, then Rule 55(b) default judgment — as an option the user confirms, with a servicemember-status caution. Never an automatic instruction to file.


PHASE 9 — Multi-agent orchestration (Harvey-style: many agents, one orchestrator)

Build a mesh of specialized agents coordinated by one orchestrator, each as a Supabase Edge Function (or a role the orchestrator invokes through router):


Navigator (orchestrator): the only agent the user talks to. Owns case state, plans the next step, dispatches to sub-agents, returns plain-language results + next-step rows. Human confirmation checkpoint between steps.
Intake agent: runs the case-type intake script, fills the case object.
Document/parsing agent: ingests uploads (credit reports, citations, orders), extracts structured data, flags issues.
Research agent: finds candidate authorities (Perplexity for open web, Gemini for the case file).
Drafting agent: Claude (per router tiering) — complaints, letters, motions, forms.
Verification agent: the Phase 7 gate. Deterministic.
Deadline agent: the Phase 8 engine. Deterministic.
Compliance/guardrail agent: see Phase 10.
Workflow agents: one per case type (Phase 11–13), each a controller calling Research → Drafting → Verification → Deadline as needed.


Standard flow: user → Navigator → intake/workflow agent → research → drafting → verification → deadline → compliance gate → Navigator → user confirms.


PHASE 10 — Compliance / guardrail agent

Inspects every drafted output before it reaches the user or a filing:


Blocks all frivolous and pseudolegal arguments, specifically sovereign-citizen theories: right-to-travel-means-no-license, "natural man vs. legal fiction," "refuse for cause," "no injured party means no crime," capital-letters-name arguments, "notice to principal is notice to agent." When detected, briefly explain why these arguments fail in court and redirect to legitimate defenses.
Enforces the "not legal advice / not a law firm" framing app-wide.
Runs a pre-filing certification before any document can be marked ready to file: every citation re-verified, deadlines confirmed, and a plain-English checklist the user confirms.



PHASE 11 — IFP workflow (fee waiver — simple side item)

A workflow agent, runnable standalone or inside a case. Asks: household size, income, monthly expenses, assets, public benefits. Then explains how courts typically evaluate fee-waiver eligibility — NEVER a flat "you qualify" (IFP is discretionary). Then drafts the application (federal form AO 240 under 28 U.S.C. § 1915, or state equivalent) as a printable document the user files alongside their complaint.


PHASE 12 — FCRA / credit repair workflow (flagship)

Built on 15 U.S.C. § 1681e(b): consumer reporting agencies must follow reasonable procedures to assure "maximum possible accuracy."


User uploads their credit report → parsing agent extracts tradelines and flags inconsistencies: not-mine accounts, wrong balances, duplicate or re-aged collections, mixed-file errors, bad dates, and cross-bureau mismatches between Equifax, Experian, and TransUnion.
Draft the three-step administrative process: dispute letters to the bureaus (§ 1681i), then to the furnisher (§ 1681s-2(b)). Deadline agent tracks the 30-day investigation clock.
If items come back "verified" but wrong, or deadlines are blown → assemble those facts into a verified complaint (FCRA claims, plus FDCPA if a debt collector is involved). Every statutory and case citation passes through the verification gate.



PHASE 13 — Traffic ticket workflow (evidence and procedure ONLY)

Strictly legitimate defense — the compliance agent blocks any sovereign-citizen argument in this workflow especially.


Capture the citation (photo upload or manual entry) → parsing agent extracts offense, code section, date/time/location, alleged speed, measurement device, officer.
Classify the speed law: absolute, presumed, or basic — this determines available defenses.
Guide the not-guilty plea and track the trial date (deadline agent).
Generate a written discovery request to the prosecution: radar/lidar calibration and maintenance records, device certification, officer's notes and training records. Track the response deadline; if records aren't produced, guide a motion to exclude or dismiss.
Build the defense around the weakest element (identity or speed): calibration gaps, device/pacing error, officer vantage point and conditions, signage defects under MUTCD standards, procedural errors on the citation, officer non-appearance.
Prepare the user: officer cross-examination question set; trial-by-written-declaration where available (e.g., California) or defense-by-certification (e.g., New Jersey); resolution alternatives (traffic school, diversion, amendment/reduction).
Any case law is jurisdiction-specific and passes through the verification gate.
